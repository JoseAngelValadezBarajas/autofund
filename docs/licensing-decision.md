The repository is now **open source** in the legal sense. The claim made in `README.md` is backed by

## Why Apache-2.0 rather than MIT

Both were viable and the analysis below is retained rather than deleted, because the reasoning is
worth being able to re-examine. The decision came down to two clauses:

1. **The explicit patent grant.** MIT is silent on patents. Apache-2.0 grants a patent license from
   contributors and terminates it if a licensee sues over patents. For a project whose value is
   partly in its methodology — replay semantics, certification gates, reconciliation of uncertain
   orders — a downstream user is better protected by the explicit grant. The cost is that MIT is
   shorter and more familiar; the benefit is that nobody has to reason about an ambiguity.

2. **The explicit exclusion of trademark rights.** Section 6 states that no trade name, trademark or
   product name is licensed. That matters for a project that names third-party exchanges throughout
   its documentation and code. It makes it unambiguous that interoperability with a venue's public
   API is not an endorsement, in either direction.

The acknowledged downside: Apache-2.0 imposes a change-notice obligation that MIT does not, and its
length means contributors rarely read it. That was judged acceptable for a project that already
expects contributors to read a substantial `CONTRIBUTING.md`.

## What this means in practice

| Question | Answer |
|---|---|
| Can someone run AutoFund on their own account? | Yes |
| Can someone sell a service built on it? | Yes |
| Must they publish their changes? | No (no copyleft) |
| Must they keep the copyright notice and license text? | Yes |
| Must they state what they changed? | Yes — this is the Apache-2.0 addition |
| Is a patent license granted? | Yes, with a retaliation clause |
| Are trademark rights granted? | No, explicitly |
| Is there a warranty? | No — "AS IS" |

**Neither license prevents someone from losing money with this software.** Both are provided without
warranty, which matters more here than in most projects: AutoFund is experimental software that can
place real orders and ships no certified strategy. The disclaimer in the license is not a substitute
for the plain-language warning in [`README.md`](../README.md) and [`SECURITY.md`](../SECURITY.md).

## Third-party assets

The repository bundles no third-party datasets, images or vendored code, so no additional
attribution is required. Frontend and Python dependencies are consumed from their package managers
and are not redistributed here. The screenshot baselines and documentation images are generated by
this project from its own demo dataset. See [`public-boundary.md`](public-boundary.md).

The research conclusions in [`research-history.md`](research-history.md) are published under the same
license as the code.

## Trademarks

AutoFund is not affiliated with, endorsed by, or partnered with Bitso, Binance, Kraken, Coinbase or
any other venue. Exchange names appear because the software interoperates with their public APIs.
Section 6 of the license grants no right to use their names, and none is claimed.

## If the decision is ever revisited

Changing the license of an already-published project requires the agreement of every copyright
holder — which, once contributions exist, means every contributor. If an alternative is ever
considered, it should be done before accepting outside contributions, or with explicit sign-off in
`CONTRIBUTING.md` from the start.

## Appendix: the analysis as originally written

Retained because it records what was actually weighed, and because a future reader deciding a license

## What the choice affects

AutoFund is unusual in that two of its strongest assets are not code:

- **The code** — a research, risk, economics and execution platform.
- **The research record** — a documented series of negative results that other people can learn from,
  and a methodology for rejecting a hypothesis.

A license that forbids commercial use would block the second from being reused by a researcher at a
company. A permissive license allows someone to take the architecture and run it against their own
account without contributing anything back, which is permitted and generally considered acceptable.

## Option 1 — MIT

**Summary.** The shortest permissive license in common use. Anyone may use, copy, modify, merge,
publish, distribute, sublicense and sell, provided the copyright notice and license text are
retained. Comes with no warranty.

| | |
|---|---|
| **Length** | ~170 words |
| **Patent grant** | **No** — silent on patents |
| **Trademark grant** | No |
| **Attribution required** | Yes, in copies |
| **Copyleft** | None |
| **Compatibility** | Compatible with almost everything |

**Arguments for AutoFund.** It is the most familiar license in the Python and JavaScript ecosystems,
so a reader does not have to think about it. It maximises the chance that the methodology gets reused
and improved. For a project whose main output is a research record rather than a product, maximum
reuse is the point.

**Arguments against.** It is silent on patents. If a contributor were ever to hold a patent on a
technique used here, MIT would not grant a license to it, leaving downstream users exposed. For a
solo project with no patent portfolio that is largely theoretical, but it is the standard reason to
prefer Apache-2.0.

**Best if** you want the least friction and care most about the research being reusable.

## Option 2 — Apache-2.0

**Summary.** A permissive license in the same family as MIT, with substantially more legal
machinery. Adds an explicit patent grant and a patent-retaliation clause, requires that modified
files be marked, and requires notices to be preserved.

| | |
|---|---|
| **Length** | ~10,000 words |
| **Patent grant** | **Yes** — explicit, with retaliation if the licensee sues over patents |
| **Trademark grant** | No — explicitly excludes trademark rights |
| **Attribution required** | Yes, plus NOTICE file and change notices |
| **Copyleft** | None |
| **Compatibility** | Widely compatible; some friction with GPLv2-only projects |

**Arguments for AutoFund.** The patent grant is a real protection for downstream users, and the
explicit trademark exclusion is useful for a project that may become known by its name. It is the
standard choice for projects with corporate contributors or expectations of one.

**Arguments against.** The notice and change-marking requirements are overhead, and for a project
whose value is in the research rather than the code those obligations may discourage a casual
reuser. It is also long enough that contributors rarely read it.

**Best if** you want explicit patent protection and expect contributors or corporate users, or you
want the trademark question settled in writing.

## Considerations specific to this project

1. **The README described the project as source-available, not open source.** That wording was
   changed as part of this decision, and a test now asserts the claim and the license agree rather
   than leaving them to drift apart.
2. **The safety language in `README.md` and `SECURITY.md` is kept regardless of license.** A
   disclaimer of warranty in a license is not the same thing as telling a reader clearly that the
   software has no certified strategy and must not be trusted with capital without understanding it.
3. **Third-party assets.** The repository contains no third-party datasets, images or vendored code.
   Frontend and Python dependencies are consumed from their package managers and are not
   redistributed here, so the license choice does not need to account for bundled third-party work.
   See `docs/public-boundary.md`.
4. **The research record.** The `docs/research-history.md` findings are published under the same
   license as the code. No license here restricts reading them.

## Per-file licence headers: deliberately not added

Apache-2.0 does **not** require a header in every source file. Its appendix offers a boilerplate
notice and says to include it "in the appropriate comment syntax for the file format" — a
recommendation about how to mark a file when you choose to, not an obligation.

Adding `SPDX-License-Identifier: Apache-2.0` to every one of the ~250 source files would produce a
large diff that touches every file, would have to be kept in step by every future contribution, and
would convey nothing that `LICENSE` plus the package metadata does not already convey for the
repository as a whole. So it was not done.

What *was* done is the part that carries real information:

| Where | Declaration | Why there |
|---|---|---|
| `LICENSE` | full canonical text | the authoritative grant |
| `pyproject.toml` | `license = "Apache-2.0"`, `license-files = ["LICENSE"]` | machine-readable, and makes a built wheel/sdist carry the license |
| `frontend/package.json` | `"license": "Apache-2.0"` | the npm ecosystem's convention |
| `README.md` | names and links the license | what a human reads first |
| `CONTRIBUTING.md` | states the inbound terms | so a contributor knows before contributing |

A test asserts that no file declares a *different* license, because a conflicting header appearing
later is the failure mode that matters — an absent header is fine, a contradictory one is not. This
also means a repository contributor can decide per file to add SPDX for their own tooling without
failing the suite.

## How the decision was applied

For reference, in case a similar project needs the same steps:

1. The canonical Apache License 2.0 text was obtained from a copy verified to be unmodified — checked
   structurally, not by trusting a filename — rather than retyped, because retyping legal text risks
   silently changing it. Several packages ship the standard text with their own copyright line
   substituted into the appendix, so the source had to be checked before being adopted.
2. The only edit applied was the one the license itself instructs: replacing the bracketed
   placeholders in the appendix with the year and copyright holder.
3. `LICENSE` was added; `pyproject.toml` gained `license = "Apache-2.0"` and
   `license-files = ["LICENSE"]` so a built distribution carries it; `frontend/package.json` gained
   the same declaration.
4. `README.md` changed from *source-available* to open source, with the license named and linked.
5. `CONTRIBUTING.md` was updated so contributors know the terms their contributions are under.
6. The temporary gate that had forbidden the open-source claim while no license existed was removed
   and replaced by a durable one: it now asserts that the claim, the license file, and the package
   metadata all agree, in both directions.
